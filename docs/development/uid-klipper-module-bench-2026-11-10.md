# Tracker UID: модуль Klipper, API и откат на стенде

10 ноября 2026. Статус: функциональный экспериментальный Klipper extra, проверенный
программным стендом. Реальный Klipper/Moonraker на U1 и физическое RFID не проверены.
На принтер ничего не установлено; установленный Tracker и личная база не изменялись.

- `dev/klipper/tracker_uid.py` — автономный модуль, `load_config(config)`, только stdlib.

## Подключение и безопасность штатного пути

Конфигурация будущего модуля (не выполнять на принтере в рамках этого этапа):

```ini
[tracker_uid]
enabled: True
stale_after: 300
```

- В конструкторе регистрируются lifecycle-события и read-only webhook.
- На `klippy:connect` все объекты уже созданы, а штатный reader ещё не стартовал на
  `klippy:ready`. Проверяется SHA-256 настоящего файла драйвера по закрытому списку.
- Проверяются класс экземпляра, отсутствие instance-hook и код загруженных методов
  против кода одобренного исходника. Чужая модификация даёт `unavailable`, без остановки
  самого принтера. Глобальных патчей класса, дополнительных радио-команд и чтения NDEF нет.
- Первоначальный штатный callback может быть None. Его регистрация detector на ready
  проходит через обёртку и сохраняется. Оригинальные аргументы/возвращаемое значение не
  подменяются. UID наблюдается отдельно от результата аутентификации/разбора материала.
- События передаются через `reactor.register_async_callback`; номер поколения и sequence
  защищают от старых/переупорядоченных событий. Время фиксируется ДО очереди, а не при
  доставке: задержанный reactor не делает старое чтение свежим.
- Shutdown/disconnect/connect_error/request_restart инвалидируют статус и очередь.
  На остановке hooks не снимаются из-под активного reader thread: они остаются прозрачными
  до завершения процесса. Отключение функции/удаление модуля — через конфиг и перезапуск,
  а не горячая замена во время печати.
- Runtime-подмена одного из hooks инвалидирует UID; чужой hook не перезаписывается.

## API

`get_status(eventtime)` делает extra доступным стандартному объектному API Klipper под
именем `tracker_uid` (для Moonraker предполагается обычный objects/query и subscribe).
Отдельно зарегистрирован read-only Klipper webhook `tracker_uid/status`. Прямой вызов
handler и объектный статус проверены; настоящее HTTP/WebSocket-проксирование Moonraker
ещё не испытывалось. Не объявлять это физически проверенной сетевой интеграцией.
Никаких endpoint для сканирования, записи метки, выбора катушки или движения нет.

Схема ответа v1:

```json
{
  "schema_version": 1,
  "module_version": "0.1.0-bench",
  "state": "ready",
  "reason": "",
  "driver_version": "2.0.0.205",
  "epoch": "new-per-module-instance",
  "sequence": 5,
  "channels": {
    "0": {"state": "present", "uid": "04000102030405", "uid_length": 7,
          "sequence": 5, "age_seconds": 0.2}
  }
}
```

Всегда четыре канала 0–3. Пример выше сокращён. UID — HEX полной длины, ведущие нули
не теряются. Состояния канала: unknown, present, absent, unreadable, conflict, stale.
Состояния модуля: disabled, waiting, attached, ready, unavailable, stopped.
После stale_after UID не выдаётся как текущий (`uid=null`). Новое получение API-ответа
не обновляет возраст самого чтения. Tracker не должен удалять старое назначение при stale:
это запрет нового автоматического назначения до подтверждения, а не доказательство снятия.

## Установка и откат

Стендовая структура: `ROOT/klipper/klippy/extras/`, `ROOT/printer_data/config/printer.cfg`.
ROOT обязан содержать `.tracker-uid-simulator.json` с содержимым:
`{"kind":"tracker-uid-filesystem-simulator","version":1}`. На настоящем U1 инструмент
использовать нельзя: путей устройства/служб/OTA он не знает, проверка root обязательна.

Установка:
1. Файловый lock; запрет операции при `.klipper-running`.
2. Проверка хеша driver, отсутствие конфликтующего модуля/config/include и symlink.
3. Журнал с исходным конфигом, правами, новыми байтами и хешами до первого изменения.
4. Атомарная запись модуля, `tracker_uid.cfg` и include-блока в `printer.cfg`.
5. Повторная установка того же артефакта не меняет файлы. Другой артефакт/изменённые
   файлы требуют отдельного обновления, автоматического затирания нет.

Откат:
- Прерванная установка остаётся pending; сначала rollback, затем повторная установка.
- Возвращает прежний config побайтно либо удаляет только собственный include-блок,
  сохраняя последующие пользовательские дополнения.
- Удаляет только собственные неизменённые файлы. При конфликте предварительная проверка
  прекращает откат до изменения config. Сохранённый журнал остаётся доступным.
- Права исходного config сохраняются. Полную прошивку и драйвер не копирует/не меняет.

CLI предназначен только для уже созданной тестовой папки:

```
python dev/labs/uid_module_bench/install.py install --simulator-root PATH
python dev/labs/uid_module_bench/install.py rollback --simulator-root PATH
```

## Что ещё проверить до разрешения установки на U1

- Настоящий lifecycle Klipper/reactor и objects/query/subscribe через Moonraker в
  изолированной среде. Сейчас Printer/Config/reactor queue/web request — имитации,
  а сканирующий цикл и методы драйвера — реальные исходники со смоделированным радио.
- Фактическую версию/хеш/порядок конфигов конкретного U1, порядок connect/ready и
  восстановление после конфигурационной ошибки; никакой установки во время печати.
- Установка на реальной файловой системе: пользователь/права, overlay, reboot/OTA,
  доступ к откату при отказе старта Klipper. Файловый симулятор этого не доказывает.
- Физические метки/антенны/загрузка, стабильность UID, поддержка каскадных чипов.
- Интеграция с общей базой одного Tracker и несколькими виртуальными принтерами,
  дедупликация событий и конфликт одного UID. Инвентарь модуль не изменяет.
- Windows GUI по-прежнему не проверен; к этому модулю не относится.
