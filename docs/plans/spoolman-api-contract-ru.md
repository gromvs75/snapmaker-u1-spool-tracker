# Spoolman: результат этапа 1 и контракт интеграции

2026-11-05. Этап 1 завершён на изолированном macOS-стенде.
Код основного приложения Tracker не менялся. Этапы 2–6 ещё не реализованы.

## Проверенная конфигурация

Spoolman **0.27.1**, commit `ff8efd517b76a4b2783f29c89e9b9fbcd8cd167b`,
Python 3.12.16, зависимости из upstream `uv.lock`, SQLite. Полный upstream-сервер
с обычными миграциями и middleware, временная база, случайный порт 127.0.0.1.
Готовые клиентские ресурсы взяты из официального архива с проверенным SHA256.
Каталог производителя и проверка обновлений выключены. U1, Snorca и установленный
Tracker не запускались и не подключались. После проверки сервер остановлен.

Стенд: [contract_probe.py](../../dev/spoolman/contract_probe.py).
Воспроизведение и контрольные суммы: [README](../../dev/spoolman/README.md).
18 утверждений прошли, включая создание фикстур. Это проверка API, не проверка
готовой интеграции или пользовательского интерфейса.

## Контракт

| Операция | API v1 | Вывод |
|---|---|---|
| Проверка сервера | `GET /info`, `GET /health` | Версия доступна; никаких записей |
| Каталог | `GET /spool?limit=…&offset=…` | Массив, `X-Total-Count`; нужна обработка страниц |
| Катушка | `GET /spool/{id}` | Вложенный filament, материал/цвет, used_weight, remaining_weight, archived |
| Списание | `PUT /spool/{id}/use` | `use_weight` в граммах либо `use_length` в мм; это прибавление расхода |
| Отсутствующая катушка | `GET /spool/{id}` | 404, нельзя заменять локальной похожей катушкой |
| Недопустимые единицы | Оба поля use одновременно | 400, смешивать граммы и миллиметры нельзя |
| Измерение | `PUT /spool/{id}/measure` | В коде upstream предусмотрен gross weight; в этом этапе не вызывался, оставлен для v1.4 |

Неизвестный остаток отсутствует в JSON; это не ноль и не достаточный запас.
При расходе 8 г из исходных 5 г сервер хранит used_weight=8, но возвращает
remaining_weight=0: отрицательный остаток скрыт ограничением снизу.
Архивная катушка принимает списание — ограничение должен обеспечивать Tracker.
Восемь параллельных запросов по 1 г дали ровно +8 г на тестовой SQLite:
дельты применяются атомарно, но это не защита от повторной доставки.

## Главный результат: повтор запроса повторяет списание

Проверено на настоящем API:

1. Два запроса по 12.345 г с одним `Idempotency-Key` дали 24.69 г расхода.
2. Прокси передал 10 г на сервер и потерял ответ: расход вырос с 24.69 до
   34.69 г, хотя клиент получил разрыв соединения.
3. Слепой повтор тех же 10 г увеличил расход до 44.69 г.

В схеме SpoolUseParameters только use_weight/use_length. По проверенным исходникам
нет протокола дедупликации этой операции по клиентскому ID или API квитанции,
которая позволила бы однозначно разрешить потерянный ответ. Значения first_used /
last_used и текущего остатка для этого недостаточно. HTTP-метод PUT здесь не
означает, что запрос фактически безопасно повторять.

Решение для этапов 2–3: первая тестовая интеграция **только читает** каталог и
остатки и строит прогноз. Для этапа 4 возможна запись с устойчивой очередью,
но после начала отправки таймаут/разрыв/неоднозначный серверный ответ переводит
операцию в `uncertain`, без автоматического повтора. После падения процесса
незавершённая отправка также считается uncertain. Подтверждённые операции не
повторяются; неотправленные могут ждать восстановления связи. Разрешение uncertain
требует отдельного процесса сверки и явного выбора пользователя; нельзя делать
вывод только по изменению остатка. Автоматическое «ровно один раз» пока не обещаем.

Локальная уникальность операции и один отправитель на принтер необходимы, но
не устраняют неопределённость ответа удалённого сервера. Не использовать PATCH
абсолютного остатка или отдельное extra-поле как мнимую атомарную квитанцию.
Не компенсировать uncertain автоматическим отрицательным расходом.

## Подключение и ошибки

Spoolman 0.27.1 не имеет встроенной аутентификации (это прямо описано в upstream
security.py). Проверенный 403 — защита от чужого browser Origin, а не проверка
пароля. Нативный клиент без Origin работает без изменения CORS. TLS и
аутентификацию reverse proxy, включая 401, ещё предстоит отдельно проверить;
не утверждаем, что эти сценарии уже покрыты стендом.

Для будущего клиента: отдельные таймауты подключения/ответа, отсутствие скрытых
повторов записи, проверка сертификатов HTTPS, запрет автоматического переноса
секретов при redirect на другой адрес, исключение секретов из логов/backup.
На этапах чтения сетевые ошибки показываются как недоступность/устаревшие данные.
Политика повторов чтения не должна применяться к списаниям.

Привязка катушки включает ID настроенного сервера и spool ID. Один материал
или цвет не заменяют эту идентичность. Передача расхода остаётся исключительной
ролью Tracker для данного U1; при другом отправителе используется только чтение.

## Лицензия и пределы проверки

Используем собственный код клиента и документированный API отдельного Spoolman.
Upstream имеет MIT; его исходники и зависимости в сборку Tracker не включены.
При будущем включении чужого кода нужно сохранить уведомления и проверить
лицензии включаемых компонентов.

Не проверены: Windows GUI, реальная нарезка Snorca на Windows, HTTPS/proxy auth,
PostgreSQL/MySQL, совместимость других версий Spoolman, длительная работа и
реальный принтер. Поведение материала/цвета в штатном API U1 этим стендом
не исследовалось. Проверку расхода по весам v1.4 не реализовывали.
