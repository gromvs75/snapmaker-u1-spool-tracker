# Ошибка, продолжение и завершение печати — исправление после rc3

База: rc3, коммит cec29f42473e3705bd67d4079c22ad6c4bf18d30.
Работа в отдельной ветке fix/rc3-resumed-print-accounting. Реальный принтер,
установленное приложение и пользовательские базы не использовались.
Присланный журнал содержит запуски rc1 и rc3, но не содержит достаточной
телеметрии, чтобы доказать точную причину конкретной печати тестировщика.
Ниже — воспроизведённые синтетические случаи, соответствующие описанию проблемы.

## Причины и изменения

1. MotionLifecycle считал error окончательным состоянием истории. Переход той же
   идентичности job_id/start_time/filename в completed возвращал Terminal history
   changed. Теперь error → completed/cancelled допускается при сохранении исходной
   привязки и всех проверок непрерывности. Разные задания по имени не объединяются.
2. HistoryReview сохранял первую ошибку через INSERT OR IGNORE. Теперь завершение
   той же записи обновляет её статус; поздняя старая ошибка его не откатывает.
3. Уже завершённое задание с сохранённым mapping_valid оставалось недоступно для
   ручного учёта без разрыва соединения. Теперь терминальная история открывает
   проверку. Перед записью по-прежнему проверяется актуальное состояние доступного
   принтера; печать и пауза блокируют списание. Финальная квитанция неизменяема.
4. Запись без наблюдавшегося старта открывалась только как справка. Добавлено
   «Указать катушки и расход»: отдельный черновик для точной идентичности истории,
   явный выбор катушек и дополнительного расхода, без подстановки текущих назначений.
   Этот путь не даёт разрешения автоматическому сборщику и не меняет остатки при
   открытии. Подтверждение использует существующую транзакцию и очередь Spoolman.
5. После сброса счётчика принтер мог сообщать только расход последнего отрезка.
   Теперь сборщик сохраняет признак уменьшения счётчика, в том числе в сообщении
   о продолжении. При сбросе либо несовпадении агрегатного счётчика с непрерывным
   потоком для ручного назначения не используется неполный счётчик истории.
   Допускается существующая оценка по проверенному полному G-code, только после
   успешного завершения и проверки неизменности файла, головок, подачи и катушек.
   При недостаточном подтверждении остаётся ручная проверка.

## Доказательства стенда

- output/resumed-print-before.log: три воспроизводящих теста падают на исходной rc3.
- tests/test_resumed_print_live.py: настоящие сборщики HTTP/WebSocket, локальный
  симулятор U1, временная база, ручная катушка без RFID. Варианты: счётчик сохранён;
  сброшен при продолжении; сброшен без отдельного уведомления о нуле. После
  завершения, повторного подключения и открытия базы — одно списание.
- output/resumed-print-live/*.json: итоговые записи синтетических заданий и расхода.
  150 мм в первом варианте дают 447 мг. В вариантах с неполным счётчиком используется
  проверенный тестовый план 18 420 мг, а не только последние 50/200 мм.
- tests/test_history_only_review_ui.py: реальный локальный HTTP-интерфейс в Chromium
  и Spoolman-симулятор. Явный выбор катушки, ввод 3,5 г, одна отправка, потеря ответа
  браузеру и повтор, обновление истории, восстановление бэкапа и открытие базы.
  Spoolman: 500 → 496,5 г, одна запись. Снимки: output/resumed-print-ui/.
- tests/test_resumed_print_accounting.py: отсутствие автослияния разных ID,
  запрет учёта при печати/паузе, повторное открытие черновика, повтор подтверждения,
  гонка с существующей привязкой и запрет позднего автоматического учёта.

Результаты: первый профильный прогон — 124 passed; UI и передача в Spoolman —
6 passed; общий прогон — 1436 passed / 3 skipped (233,53 с),
output/resumed-print-full-tests.xml. После расширения проверки на сброс без
уведомления о нуле отдельно пройдены все три сетевых сценария и регрессия
расчётного учёта/отчётов Windows: 82 passed (26,95 с),
output/resumed-print-counter-final.log. Общий прогон не включал этот последний
добавленный вариант; он покрыт указанным дополнительным прогоном.

Это исправление исходников, не новый выпущенный EXE/.app. Выданные архивы rc3
не изменялись. Нативный Windows GUI именно с этим исправлением ещё не проверен;
проверка в Chromium его не заменяет. Новые сценарии добавлены в сборочный workflow.
