## Важно: исправления после выпущенной 1.3.2

Перед будущей интеграцией прочитать
[post-1.3.2-port-to-2.0.md](post-1.3.2-port-to-2.0.md): отдельные rc2–rc4 содержат
исправления Windows/трея, производителя Spoolman и новый экран сравнения имён,
которых нет в базе 1.3.2. Там перечислены ветки, коммиты, проверки и отдельные
незавершённые исследования ручной замены/автодозаправки. **Сейчас не объединять:
2.0.0 ещё в разработке, ждём ответа пользователя по rc5.** После отзыва на rc4
подготовлена `ui/spoolman-rc5`: компактный тёмный диалог и поиск Spoolman.
При переносе брать rc5 UI вместо прежнего rc4; детали и commit — в списке выше.

Продолжаем разработку Snapmaker U1 Spool Tracker 2.0.0 в
`/Users/viktor/snapmaker-tracker`. Сначала только изолированный стенд.
Не подключаться к реальному U1, не менять установленный Tracker, пользовательские
настройки или базу. Ничего не публиковать. Соблюдать AGENTS.md; репозиторий содержит
много прежних незакоммиченных изменений — не сбрасывать их и не переносить массово.

Цель: один Tracker, несколько принтеров с постоянными ID, именами и адресами;
общая база катушек по UID, автоматическое узнавание после переноса и сохранение
остатка. Существующие ручные назначения и функции учёта должны сохраниться.

Уже сделано:

1. `dev/klipper/tracker_uid.py`: отдельный Klipper extra, обёртка в памяти без
   изменения файла RFID-драйвера. UID+канал, epoch/sequence, read-only API.
   `dev/labs/uid_module_bench/install.py`: установка/откат только маркированного
   файлового симулятора. Это не установщик реального принтера.
2. `dev/labs/uid_live_bench/`: запуск настоящих Klipper/Moonraker на Mac с
   симуляцией RF/SPI/GPIO/MCU. 23 интеграционные проверки.
3. `src/tracker_uid_client.py`: независимые WebSocket подключения, повторное
   подключение, полные снимки и подписки, UUID сеанса клиента, поколение соединения,
   epoch, свежесть. `src/tracker_uid_catalog.py`: SQLite-каталог UID/spool_id/остаток
   и положения, защита от конфликтов. `dev/labs/uid_multi_bench/`: 19 проверок
   переноса катушек и отказов на двух реальных процессных парах.
4. `src/tracker_uid_accounting.py`: `TrackerUidService`, привязка задания на старте,
   atomic SQLite журнал/остатки, cumulative расход по головкам, дельты, защита от
   повторов, отмена и перенос. `dev/labs/uid_accounting_bench/`: 14 проверок.
   Чёрная: 500−30 (отмена)−10 (после переноса)=460 г;
   оранжевая: 300−20=280 г. Повторы не изменяют баланс.
5. 262 автоматических теста прошли. Команда:
   `/private/tmp/tracker-uid-live/env/bin/python -m pytest tests/test_uid_accounting.py tests/test_uid_client.py dev/labs/uid_module_bench dev/labs/uid_bridge_bench -q`.

Ограничения: новый сервис не подключён к рабочему GUI/реальному сборщику расхода.
В последнем стенде события расхода синтетические, доставляются через тестовый API;
это не тест настоящей печати. Импорт старого снимка поддерживает только пустую
историю, все катушки с явно назначенными UID и пустую целевую SQLite-базу;
история/нетегированные катушки/Spoolman send требуют полноценной миграции.
Исходный JSON сохраняется целиком, ID и остатки сохраняются. Продукционной миграции
пользовательской базы ещё не было. Windows GUI и реальное чтение сторонних меток
не проверены. Поддержку любой NFC/RFID не обещать.

Согласованный первый шаг в новом чате:
изучить актуальный сборщик и расчёт расхода, включая исправление отменённых
печатей, затем сделать его стендовый адаптер к TrackerUidService. Определить
доступные идентификаторы задания, наблюдённый старт, накопительный расход по
головкам, завершение/отмену и признаки разрыва наблюдения. При недостатке данных
сохранять причину неопределённости, не вычислять расход по проценту готовности.
Сначала проверить адаптер на сохранённых фикстурах/симуляторе, включая два
параллельных задания, отмену, перенос, рестарт клиента и повторную историю.

При предыдущем исследовании читались исходники исправленной сборки из
`output/cancel-accounting-fix-2026-11-10/src/` (accounting.py, storage.py и др.).
Не путать их с прежними файлами в корне: сначала сверить актуальную версию.
Новые модули 2.0 находятся в src/. Не переносить весь старый проект автоматически.

Дальнейшая последовательность:
- адаптер существующего источника расхода к нормализованным событиям нового сервиса;
  не заменять расход по головкам процентом печати или одним общим filament_used;
- полноценная миграция базы с backup/restore и переносом защиты от повторов,
  граница переключения старого/нового учёта, без двух одновременно пишущих систем;
- ручные назначения и разрешение неоднозначностей, затем интеграция GUI;
- все проверки сначала на стенде, реальный принтер только по отдельному поручению.
