# Восстановление по истории: первый этап, 14.11.2026

Ветка `integrate/2.0-history-recovery`, checkpoint
`checkpoint/2.0-before-history-recovery-2026-11-14` (b6093d3).
Локальная разработка; отправки ветки, Actions и публикаций нет.

## Реализовано

- Независимый history/profile reader сохраняет проверенный план активного задания
  (SHA-256 файла, масса по инструментам, параметры материала и mapping) через очередь
  единственного SQLite owner. Требуется уже наблюдённый старт и однозначная history
  identity. Поздняя история не создаёт привязку катушки задним числом.
- Таблица uid_recovery_profiles сохраняется при перезапуске; изменённый план
  помещается в карантин. Restore резервной копии также помещает планы в карантин.
- History binder принимает error/shutdown/disconnect/interrupted для дальнейшего
  рассмотрения; рабочий motion-дебет от этого не получает новых разрешений.
- Read-only recovery_preview выбирает положительный счётчик истории для задания
  с одним использованным инструментом. Перевод в мг использует сохранённые параметры.
  Для completed без подходящего счётчика предлагает полный план слайсера.
- Для прерванного задания без подходящего счётчика можно явно указать слой и получить
  диапазон плановой экструзии. Номер остановки не выдумывается из процента печати.
- Разбор поддерживает явные SET_PRINT_STATS_INFO CURRENT_LAYER, M82/M83,
  G90/G91, G92 E, T0–T3 и E-движения. Неизвестная/неподдерживаемая форма экструзии,
  масштабирование, volumetric и firmware retract исключают эту оценку.
  Макросы прошивки, служебная загрузка и физическое проскальзывание не измеряются.

## Что намеренно ещё не подключено

Это основа восстановления, **не законченный пользовательский сценарий**.
Нет recovery-дебета, GUI подтверждения и автоматического применения предложения.
Все previews имеют authorizes_debit=false и requires_confirmation=true.
Источник расхода не доказывает, что во время разрыва не заменили катушку.

Пользователю задан вопрос: при сомнении в катушке требовать ручную сверку
(рекомендуемый режим) либо для одной назначенной катушки принимать предположение
о её неизменности во время сна. Ответ пока не получен. Это влияет на условие
автоматического списания, поэтому рабочие ограничения не ослаблены.

Перед применением потребуется актуальная проверка mapping/назначений, отдельное
подтверждение для неопределённости, ревизия предложения и атомарная запись receipt
в общем ledger. Одного положительного счётчика для решения недостаточно.
Наблюдённые automatic/mapping/identity проблемы уже блокируют preview.
Автодозаправка T3→T1 не разблокирована.

## Проверки

Полный набор до дополнительных отрицательных тестов: 734 passed, 5 skipped,
74.26 s. После уточнения синтаксиса и добавления отрицательных тестов выполнен
выборочный набор recovery/collectors/lifecycle/backup (результат в журнале чата).

Два настоящих no-hardware Klipper/Moonraker (18791/18792), временная SQLite:
Tracker запущен до старта; оба плана сохранены; весь Session/owner закрыт;
принтер A завершил, B отменил печать; новый Session получил историю.
Четыре проверки прошли: восстановление обоих заданий, обоснованные предложения,
повтор истории без дебетов, отсутствие Spoolman outbox.
В успешном запуске A дал 298 мг по истории. Для B при нулевом счётчике использован
явно выбранный слой с диапазоном 0–298 мг. Это оценка G-code, не фактическое измерение.
Обе катушки остались по 500000 мг. Все стендовые процессы остановлены.

Артефакты: output/history-recovery/, output/history-recovery-process.log,
output/history-recovery-tests.log. Генерируемые файлы не коммитятся.
Установленный Tracker, пользовательская база и реальный принтер не использовались.

Изменение схемы: старые backup-пакеты без новой таблицы пока отвергаются существующей
строгой проверкой равенства схем. Совместимость таких копий требует отдельной миграции
перед выпуском; это не готовая сборка для замены установленного приложения.

Продолжение: пользователь разрешил расчётный путь, включая подтверждённую
автозамену. [Второй этап](calculated-history-accounting-2026-11-14.md) добавляет
автоматическое применение для завершённых заданий с подтверждёнными UID.
Ожидание прежнего вопроса больше не актуально; ограничения ручного распределения
и GUI описаны во втором отчёте.
