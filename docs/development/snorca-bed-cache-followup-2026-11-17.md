# Почему rc15 не определяет стол в реальной нарезке Snorca

Проверка 17.11.2026. Только чтение присланных G-code, Dragon_stan-U1.3mf и
временного проекта Snorca `10_23_08#78999#52`. Принтер, Tracker и его база
не запускались и не изменялись. Код приложения и сборка не менялись.

## Доказательства

| Экспорт | Временный файл | SHA-256 обоих файлов |
| --- | --- | --- |
| Assembly_PLA_1h47m.gcode | .78999.0.gcode | 2e242f92e55cf0a0112fa944daefcf4d044cf830a68246898d9c566b74ab52d6 |
| d4046d31367295d6aa314263cac457a4_PLA_3h16m.gcode | .78999.1.gcode | 1316c508411a9c6495aa9d6441f1e98f403b94ba168b4ff97cffac7cd764d78c |

G-code не содержит явного номера стола. Вектора плана: [0,0,48.42,0] г
и [63.55,2.75,11.83,0] г. Это индексы материалов проекта, сами по себе
не подтверждающие физическую привязку к головкам при отправке.

Во временной `.3mf` есть plater_id 1 и 2, но оба gcode_file пусты.
Её mtime = 1794907436.8960483; G-code mtime = 1794907528.4025843 и
1794907543.20844. Резервная копия предшествует нарезке. Свежих config.3mf
или отдельного model_settings.config в этом проекте не обнаружено.
Поэтому rc15 отбрасывает старую копию; даже снятие проверки времени не
поможет: прямые ссылки на G-code отсутствуют.

Присланный сохранённый Dragon_stan-U1.3mf тоже не содержит gcode_file.
Состав объектов позволяет человеку сопоставить этот конкретный пример:
стол 1 — Assembly (48.42 г), стол 2 — d4046d31367295d6aa314263cac457a4.stl
(78.13 г суммарно). Но это не универсальный алгоритм идентификации.

G-code EXCLUDE_OBJECT_DEFINE использует имена с id_0_copy_0 в обоих файлах;
эти индексы не равны object_id/identify_id из проекта. В экспортированном
3MF object_id = 4/2, identify_id = 695/170; во временном проекте = 12/9
и 104/93. Нельзя считать их стабильными сквозными идентификаторами.

## Вывод и оставшаяся работа

rc15 устранил ложную нумерацию по счётчику временных файлов, но НЕ решил
автоматическое определение столов обычной фоновой нарезки Snorca.
Предыдущие тесты с явным gcode_file проверяли поддерживаемый формат,
а не наличие этого формата в реальном рабочем сценарии.

Не перенумеровывать найденные файлы по порядку, не угадывать по цвету,
расходу или названию объекта. Требуется исследовать источник явной связи
в момент нарезки либо обеспечить передачу номера из слайсера. До этого
не обещать автоматические номера; неизвестные файлы должны различаться
полным именем/данными модели, без фиктивного номера стола.
Нужны проверки одинаковых объектов на разных столах, одиночной нарезки
стола 2/3, перестановки столов и повторной нарезки до новой сборки.
