# Несколько сборщиков, история и один SQLite-поток

10 ноября 2026. Реализован `src/tracker_uid_runtime.py`. Проверки только offline:
реальный принтер, установленный Tracker, пользовательские настройки/БД не
использовались. Ничего не опубликовано.

## Подключение

`AccountingOwner(path, fleet)` создаёт поток `uid-sqlite-owner`. Каталог,
соединение SQLite, TrackerUidService, адаптер и MotionLifecycle создаются внутри
этого потока; там же выполняются все операции и закрытие соединения. Стандартная
проверка SQLite check_same_thread остаётся включённой. Соединение наружу не выдаётся.

`QueuedLifecycle` заменяет прямые вызовы lifecycle из сборщика. Он копирует
аргументы и UID-снимок в момент подачи события, ставит команду в ограниченную
очередь и ждёт Future с результатом. Поэтому задержка очереди не подменяет
стартовый UID более поздней катушкой. Все команды исполняются последовательно;
история из другого потока может приходить до или после terminal evidence.

`PrinterWorkers` запускает для постоянного printer_id два независимых потока:

- motion: создаёт сборщик с QueuedLifecycle, читает отдельный сокет, повторяет
  подключение после ошибки; start/terminal/disconnected идут через очередь;
- history: вызывает только переданный read-only history_reader и отправляет
  полный пакет в очередь. Старый poll_once и legacy-списание не вызываются.

Transport/recorder factories, config и history_reader передаются явно. Для
стендового сборщика factory создаёт MotionStreamRecorder с lifecycle, printer_id
и разрешёнными каналами. Для реального HTTP-клиента интерфейс reader совпадает
с MoonrakerClient.history, но в этом прогоне передавался симулятор. Поиск
установленных настроек и автоматическое подключение к адресам отсутствуют.

Пример композиции (использовать только явно подготовленные стендовые factories):

```python
owner = AccountingOwner(bench_database_path, uid_fleet)
workers = [
    PrinterWorkers(owner, pid, recorder_factory, socket_factory, history_reader, config)
    for pid, recorder_factory, socket_factory, history_reader, config in bench_printers
]
try:
    for worker in workers:
        worker.start()
    # Управляющий код стенда ждёт проверяемые результаты через owner.call('inspect').
finally:
    for worker in workers:
        worker.stop()
    owner.close()
```

Нужен ровно один owner на базу. Сначала останавливаются producers, затем owner:
принятые команды выполняются перед закрытием SQLite. Новые команды после close
отклоняются. При остановке оставшиеся active-привязки инвалидируются. Если worker
не завершился за timeout, stop сообщает ошибку; закрывать owner при живых producers
нельзя. Сетевые зависимости обязаны иметь ограниченные тайм-ауты; motion socket
закрывается при stop, а история должна вернуться по своему I/O timeout.

## Переподключение и ошибки

Ошибки соединений доставляются в owner как disconnected и сохраняются как
причины review. Motion restart посреди printing не создаёт нового наблюдённого
старта. Разрыв history также консервативно блокирует текущую active-привязку;
последующая успешная история не снимает блок. Другие принтеры продолжают работать.
Возобновление требует нового подтверждённого задания либо будущего ручного review.

При штатном исчерпании очереди producers ждут места; события не отбрасываются.
Каждое обращение получает результат или исключение. Ошибка одной команды не
завершает SQLite worker. Данные копируются, producer не может изменить уже
поставленный payload. Очередь находится в памяти: принудительное завершение
процесса может потерять ещё не записанное событие. При повторной доставке SQLite
квитанция предотвращает повторное списание; после рестарта активные привязки
консервативно инвалидируются. Это не дисковый журнал входящей очереди.

## Стендовые проверки

`tests/test_uid_runtime.py` запускает два экземпляра исправленного сборщика из
`dev/labs/uid_motion_bench/recorder_fixture.py` в двух motion-потоках и два
history-потока. Поддельные сокеты передают настоящие структуры подписок/status/
trapq. Расчёт длины, граница отмены, пересчёт массы, lifecycle и SQLite исполняются
обычным кодом; сетевого обращения нет. Старые функции списания в тесте запрещены.

Проверено:

- Отказ первого подключения и успешный retry: две катушки списывают по 0,298 г.
  Остатки 499,702 и 299,702 г; ровно две записи в журнале.
- Обрыв после наблюдённого старта первого принтера: повторное подключение не
  создаёт новую привязку; первый остаток 500 г, второй 299,702 г, одна запись.
- Параллельная доставка 20 повторов истории из четырёх producers и повтор после
  открытия базы новым owner: количество списаний и остатки не меняются.
- Четыре producer thread ID отличаются от SQLite owner; check_same_thread не
  отключается. После остановки ни owner, ни producers не остаются живыми.
- Payload и UID snapshot меняются у producer, пока owner занят: старт получает
  исходные данные; следующая UID-смена инвалидирует привязку без перепривязки.
- Ошибка history HTTP фиксируется, опрос возобновляется, разрешение не возвращается.
- Неизвестная команда не убивает owner; close обрабатывает ранее принятые команды
  и запрещает новые. Legacy JSON-остатки не изменяются.

Запуск в окружении с pytest и filelock:

```sh
python -m pytest tests/test_uid_runtime.py -q
```

Полный набор данного этапа: runtime + lifecycle + motion_adapter + uid_accounting
+ uid_client + stream_accounting + motion_analysis + motion_allocation +
uid_module_bench + uid_bridge_bench. Вывод: `output/uid-runtime-bench/tests.txt`.
Локально filelock был взят из временного прежнего test-env через PYTHONPATH;
зависимости установленного Tracker не менялись.

## Границы

Рабочий GUI и установленные сетевые workers не переключены. Реальные процессы
Klipper/Moonraker в этом этапе не запускались: проверяется многопоточная интеграция
на offline транспортах. Миграция пользовательской базы, переключение единственного
writer в установленном приложении, ручное разрешение блокировок и Spoolman outbox
остаются отдельными этапами. Windows GUI, физическая печать и RFID не проверены.
