## Реализация

Snorca уже подставляет настоящий `plate_number` в стартовый G-code. В отдельном
профиле/копии проекта добавляется только комментарий:
`; TRACKER_BED_V1 = {plate_number}`. Это не патч прошивки или слайсера.
Tracker читает его внутри EXECUTABLE_BLOCK той же завершённой неизменной копии
байтов, по которой вычисляет SHA-256 и веса. Номер не выводится из имени
файла, модели, цвета, порядка или расхода. Формат — display metadata, не
подтверждение физического mapping/UID и не разрешение списания.

Повторные, некорректные и неподдерживаемые маркеры дают неизвестный номер.
Шаблон в CONFIG_BLOCK не считается маркером завершённой нарезки. При отсутствии
маркера сохраняется прежнее чтение прямых свежих ссылок проекта. Изменение
порядка столов требует повторной нарезки; старый файл описывает старую нарезку.

## Реальный движок Snorca

`dev/run_bed_identity_lab.py` использует установленный бинарник только для
изолированного CLI, заводские профили и синтетические кубы. `sandbox-exec`
запрещает сеть и запись вне нового временного каталога; оба запрета проверяются
перед запуском. Пользовательские настройки не читаются.

Шесть сценариев прошли: все столы → 1/2/3; только второй → 2; только третий → 3;
повторная нарезка третьего → 3; перестановка разного размера кубов → корректные
номера и соответствующие веса; профиль без маркера → неизвестные номера.
Одинаковые имена и одинаковые модели не смешивают столы. Затем файлы копируются
в произвольные GUI-подобные имена `.900.47.gcode` и т.д.; observer получает
правильные номера. Повторный poll не создаёт новых событий.

Исполняемые команды всех трёх файлов побуквенно совпали с контрольной нарезкой
без маркера (комментарии исключены из сравнения).
Отчёт: `output/bed-marker-engine-report.json`; журналы в указанном там temp root.
