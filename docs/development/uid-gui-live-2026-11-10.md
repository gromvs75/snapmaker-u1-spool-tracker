# GUI 2.0 на двух процессных стендах — 10 ноября 2026

Проверена цепочка GUI → HTTP bridge → единственный AccountingOwner SQLite →
ModelInventoryStore → два сборщика MotionStreamRecorder → два настоящих
Klipper/Moonraker и их история. Реальный принтер, установленный Tracker,
пользовательская база и настройки не использовались.

## Результат

Финальный прогон: 11 процессных проверок и 26 проверок браузерного GUI прошли.
Регрессия: 396 тестов pytest прошли за 18.84 с.
Четыре переноса выполнены через GUI (туда/обратно до и после переподключения
между заданиями); повторы request_id не добавили операции переноса.

|---|---:|---:|---|
| manual-a | 500000 | 499702 | 1 × 298 мг |
| manual-b | 300000 | 299404 | 2 × 298 мг |

Два первых параллельных задания связаны с настоящими history ID Moonraker;
отмена A и завершение B создали по одному списанию. Пять повторов истории не
изменили результат. Во второй паре заданий Moonraker A остановлен во время
наблюдения; B успешно завершился и списал расход один раз. A переподключился,
но потеря непрерывности сохранила запрет списания. Нового старта от reconnect
не возникло. После остановки сборщиков, переоткрытия SQLite и трёх повторов
каждой истории осталось ровно три списания. `PRAGMA integrity_check`: `ok`.

GUI проверен на живых ответах без подмены /api/state: обязательное подтверждение,
занятая головка, drag-and-drop, повтор переноса, запрет переноса при печати в UI
и API, offline, сброс доверия ручного назначения, повторное подтверждение после
idle reconnect и перезапуска владельца базы. При разрыве одного принтера другой
оставался доступным. Снимки сохранены для всех основных состояний.

## Исправления

1. Новый интеграционный launcher сначала унаследовал старую Store-фикстуру с
   фиксированными ID spool0…spool3. Учёт безопасно отклонил старт: manual material
   snapshot не совпадал с назначением GUI. Подключён ModelInventoryStore, читающий
   фактические назначения 2.0 через очередь. Повторный полный прогон успешен.
2. Повторные ошибки подключения добавляли одинаковую причину проверки в SQLite
   на каждой попытке. Теперь сохраняется одна запись на пару job_key/reason;
   разные причины сохраняются. Финальный процессный прогон подтвердил отсутствие
   повторов; добавлен тест 50 повторных разрывов и новой независимой причины.
3. GUI показывал «Печать активна» для задания с потерянной непрерывностью.
   Теперь явно показывает «Прерванное задание — перенос заблокирован» и статус
   катушки «Прерванное задание — нужна проверка».

## Существенное ограничение

`server_exit` означает остановку Moonraker, а не обязательно физическое завершение
печати. Поэтому после разрыва во время печати катушка остаётся зарезервированной
для проверки; GUI не предлагает автоматически снять такую блокировку. Ручное
разрешение прерванного задания ещё не реализовано. Это сохраняет защиту от
списания недоказанного расхода и небезопасного переноса. Переподключение между
заданиями проверено отдельно: после подтверждения перенос работает.
