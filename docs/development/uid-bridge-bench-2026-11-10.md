# UID bridge: стенд, 10 ноября 2026

## Результат

72 теста прошли на Python 3.11. Проверены программные тракты на снимках драйвера
Snapmaker 1.3.0.168, 2.0.0.205 и 2.1.0.157, поставляемых в тестовом корпусе Bespok3d.
Для каждого снимка патчи применены в отдельную временную копию с `patch -f -F0`.
Это проверка совместимости с данным корпусом исходников, не с прошивкой реального U1.

Настоящий фоновый цикл драйвера обходит каналы, выполняет повторы, обрабатывает ошибку
аутентификации и вызывает callback. Подменены SPI/GPIO, активация карты, ответы чтения,
ожидания, окружение Klipper и криптографический разбор оригинального содержимого.
Настоящее радио, расположение антенн, считывание при загрузке пустой катушки и стабильность
UID физического чипа не проверялись. Подключений к принтеру и изменений Tracker/катушек нет.

## Что обнаружено

| Сценарий | Bespok3d в проверенной конфигурации | Стендовый UID-адаптер |
|---|---|---|
| Чужая Mifare Classic, 4 байта UID, ошибка ключа | Без claim-handler UID не выходит: fallback ограждён `if self._card_claim_handlers` | Регистрирует обработчик, отказывающийся от разбора; включается штатный для патча UID fallback |
| Та же Mifare с зарегистрированным claim-handler | UID-only передаётся в detector, материал NONE | Сохраняет UID и канал независимо от материала |
| Пустая NTAG с 7 байтами UID, пустой NDEF | Чтение страниц успешно; NDEF-декодер возвращает ошибку; CARD_UID в detector остаётся 0 | Забирает UID из страниц 0–2 до разбора NDEF, проверяет оба BCC |
| Усечённые страницы, неверный BCC, нулевые данные | Не используются как доказательство личности | Нет UID, состояние unreadable |
| Mifare с префиксом случайного UID 08 | Патч не выдаёт устойчивую идентичность | Нет автоматической привязки |
| Перенос 0 → 3, очистка, ошибка чтения | Пройдены через callback | UID сохранён, канал изменён; clear=absent, ошибка=unreadable |
| Перезапуск | — | Новый epoch, все каналы unknown; старое состояние не переносится |

Предыдущее утверждение «в Bespok3d уже есть UID-only» требует уточнения: функция есть,
но регистрация одного NtagReader не активирует ветку Mifare fallback. Это обнаружил
именно прогон фонового цикла, а не изолированная проверка helper-функции.

## Минимум, подтверждённый этим стендом

1. Патч только `fm175xx_reader.py` с точной проверкой совместимости. В стенде используется
   существующий патч Bespok3d целиком, НЕ заявляется минимальность каждой строки diff.
2. Отдельный UID-модуль: регистрация Mifare fallback; обработчик Type2, читающий только
   первые 4 страницы; проверка UID; сохранение пары канал/UID в собственном статусе.
3. Подключение модуля через конфиг Klipper и перезапуск Klipper (на принтере НЕ выполнялось).

На отдельном наборе тестов оставлен НЕПАТЧЕННЫЙ `filament_detect.py`, отключены hub и
парсеры Bespok3d. Оба типа меток дают UID нашему адаптеру во всех четырёх каналах.
`print_task_config`, pressure advance, таблицы материалов, Spoolman Bridge, полный daemon
Bespok3d и декодеры производителей для этого программного пути не нужны.

Это НЕ доказательство варианта «добавили только config». Ранее согласованное требование
не менять файл штатного драйвера остаётся открытым ограничением. Путь без записи в этот
файл (обёртки в памяти) здесь не реализован и не проверен. На реальный принтер патч не
разрешён данным исследованием. Выбор между узким патчем и обёрткой требует отдельного
решения после следующего стендового этапа.

## Чего ещё нет в прототипе

`bridge.py` — чистый адаптер событий, НЕ устанавливаемый Klipper extra. Нет `load_config`,
жизненного цикла подключения, безопасного сохранения/цепочки единственного callback
драйвера, передачи событий из фонового потока в reactor, блокировок, API Moonraker,
таймаутов состояния, установщика и отката. В тестах callback явно составлен в harness;
это не проверка его подключения к живому Klipper. Отдельный тест запрещает занимать
уже зарегистрированный Type2 handler.

Оригинальные катушки должны продолжить штатный путь; тест подтверждает передачу
успешного оригинального результата детектору с подменённым декодером. Автоматическое
объединение оригинального UID из detector с сырым UID-модулем ещё предстоит реализовать.
Mifare с 7/10-байтовым UID, каскадная активация настоящей карты, клонированные UID,
несколько меток в поле, ISO15693 и полная совместимость марок НЕ подтверждены.
Повторные одинаковые чтения должны давать idempotent-привязку в Tracker; сам стендовый
модуль выдаёт возрастающие sequence, а полноценной базы назначения в нём нет.

## Контракт для следующего этапа

В U1: `{epoch, sequence, channels: {"0": {state, uid, sequence}, ...}}`.
Состояния: unknown / present / absent / unreadable; добавить свежесть и причину ошибки.
UID — полный массив байт с длиной/типом, нормализованный HEX без потери ведущих нулей.
В Tracker printer_id задаёт запись принтера, не IP; адрес может измениться. Ключ назначения
`(printer_id, channel)`, UID ищется в общей базе. Конфликты одинакового UID на двух U1,
устаревшие данные, пропуски sequence и новый epoch блокируют автоматическое переназначение.
Один физический рулон с двумя заводскими метками может требовать нескольких UID-алиасов;
не объединять их автоматически по цвету или материалу.
