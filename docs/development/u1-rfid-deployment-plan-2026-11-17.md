# RFID на пользовательском U1: план до установки

Статус: **план с незакрытыми условиями допуска, не команда к установке**.
Разрешено только чтение. На U1 ничего не устанавливалось, режимы сохранения не
менялись, службы и принтер не перезапускались. Исходная разработка — `7cc7cf2`,
ветка `integrate/2.0-graphite-ui`, приложение остаётся rc17.

## Что теперь подтверждено непосредственно на U1

- `fm175xx_reader.py` совпадает с проверенным снимком 2.1.0.157:
  `ce7363f8b512e5474d18bd57cdf0660e6e2df57dc256e22f743b3b28c1b70be8`.
- Работающий процесс: Python 3.11, Klipper PID 1267 на момент чтения,
  `/home/lava/klipper/klippy/klippy.py`, активный `printer.cfg`.
- `/home/lava/printer_data` — символическая ссылка на `/oem/printer_data`.
  Физический основной конфиг: `/oem/printer_data/config/printer.cfg`.
- Каталог `/home/lava/klipper/klippy/extras` находится в корневом overlay.
  Верхний слой: `/oem/overlay/upper`; нижний — squashfs `/overlay`.
- PID 1 — `init`, запуск через `/etc/init.d/rcS`, затем `S60klipper` и
  `S61moonraker`. Это не подтверждённая схема systemd.
- Новый модуль и его конфиг отсутствуют. Активные include — `fluidd.cfg`,
  `xyz_offset_calibration.cfg`; конфликтов tracker в прочитанном дереве нет.

Снимок SHA-256 основного конфига:
`6979227191eb4619e1364d751f2d6fcedb3cf45ec667fb3bb8d4ea0945fe4356`.
Перед любой будущей записью требуется новая проверка, а не применение этого
хеша как вечного разрешения. Полные пользовательские конфиги не копировались;
прочитаны дерево include, хеши и признаки конфликтующих секций.

## Главный найденный риск: модуль и конфиг переживают загрузку по-разному

Прочитанный `S01aoverlayfs` при отсутствии `/oem/.debug` очищает
`/oem/overlay/*` до монтирования нового корня. На данном U1 `.debug` отсутствует.
Следовательно, добавленный в `klippy/extras` модуль не сохранится после такой
загрузки. Это вывод из исходника скрипта и фактического mount, не эксперимент
с перезагрузкой устройства.

Прочитанный `S48setup-lava-env` сохраняет пользовательский конфиг, если есть
`/oem/printer_data/.fluidd` или `/oem/.factory` (после первичной подготовки).
На данном U1 `.printer_data` и `.fluidd` присутствуют, `.factory` отсутствует.
Поэтому добавленные include и секция `[tracker_uid]` могут сохраниться,
когда Python-файл уже удалён. Возникает риск ошибки загрузки Klipper из-за
отсутствующего extra. Обработка неизвестного хеша внутри `tracker_uid.py`
не защищает от отсутствия самого модуля.

`systemUpgrade.sh` содержит удаление `.debug` и `.printer_data` в функции с
описанием действий перед активацией SOC-прошивки. Это отдельная граница:
сохранность при обычной перезагрузке не означает сохранность при обновлении.
Вызовы этой функции и все варианты обновления данным чтением не доказаны.

**Нельзя считать решением молчаливое создание `/oem/.debug`: он сохраняет
весь верхний слой системы, а не только RFID-модуль.** Даже ссылка из extras
на файл в `/oem` без сохранения самой ссылки не решает проблему.
В просмотренных init-скриптах не найден готовый пользовательский boot-hook;
проверенные пути `rc.local` отсутствуют. Это не доказательство отсутствия
любой другой точки расширения в прошивке.

## Второй риск: штатный restart имеет аппаратные последствия

По исходнику `/etc/init.d/S60klipper`:

- `stop` останавливает PID из pidfile и выключает питание main/head MCU;
- `start` включает питание, ожидает MCU, вызывает `systemUpgrade.sh`
  с `check-restore`, `check` (если не включён режим пропуска), выбирает конфиг
  по модели MCU и запускает Python;
- `restart` последовательно делает stop/start.

Маркер пропуска MCU-проверки на U1 отсутствует. Мы не создаём его и не меняем
штатные проверки. Скрипт найден и прочитан, **его остановка/запуск не испытаны**.
Нельзя выдавать его вызов за чисто программный restart без побочных действий.
Альтернативный способ остановки с учётом watchdog/lmd тоже ещё не проверен.

## Предлагаемая последовательность

### 1. Закрыть условия на стенде

Воспроизвести найденную схему squashfs + очищаемый overlay + постоянный config.
Не выполнять скопированные аппаратные скрипты на Mac/Linux-хосте; моделировать
файловый жизненный цикл в изолированном корне и использовать процессные стенды.

Обязательные сценарии:

1. Установка обычных трёх файлов при `.debug` absent: холодный старт выявляет
   исчезновение модуля при сохранении config; такой план должен отклоняться.
2. Выбранный механизм постоянной загрузки: обычный старт, потеря питания после
   каждой записи, повтор операции, откат. Нельзя оставлять активный include
   без доступного модуля при следующей загрузке.
3. Изменение прошивки/драйвера и сброс маркеров: штатный запуск без RFID должен
   оставаться восстанавливаемым; неизвестный драйвер не подключается.
4. Отмена/ошибка установки, конфликт редактирования, потеря SSH и повторный
   запуск установщика. Откат не затрагивает другие правки пользователя.
5. Остановка действительно завершается; нет второго Klipper или автоматического
   подъёма старого процесса. Зафиксировать аппаратные действия выбранного пути.

Кандидаты для отдельной оценки: явное согласованное сохранение overlay либо
поддерживаемая прошивкой выборочная загрузка из постоянного раздела, если такая
точка расширения будет подтверждена. Первый меняет системный режим глобально;
второй сейчас не найден. Ни один пока не утверждён как готовый способ установки.

### 2. Сформировать окончательный пакет и запрос разрешения

Базовые целевые изменения после закрытия пункта 1:

| Файл | Изменение |
| --- | --- |
| `/home/lava/klipper/klippy/extras/tracker_uid.py` | Новый проверенный observer; путь хранения/загрузки зависит от выбранного механизма |
| `/oem/printer_data/config/tracker_uid.cfg` | Новый конфиг модуля |
| `/oem/printer_data/config/printer.cfg` | Один маркированный include-блок |
| Механизм сохранения/загрузки | Пока не определён; должен быть отдельным видимым изменением плана |

Файл `fm175xx_reader.py` не изменяется. Перед разрешением показать полный список
изменений, их хеши, способ запуска и аппаратные последствия, расположение копий,
пошаговый откат, результаты стенда. Текущий `0.2.0-bench` не использовать на U1.
Физическая проверка требует свободного принтера; текущее состояние перед
операцией проверяется заново. Не использовать сохранённое `complete` как допуск.

### 3. Будущая установка, только после разрешения

- Повторно сверить идентичность узла, драйвер, пути, активный конфиг и отсутствие
  стороннего модуля. Существующую ссылку printer_data проверять явно, а не
  отключать запрет на любые ссылки в установщике.
- Сохранить исходный конфиг, дерево include, права, отсутствие/содержимое
  целевых файлов и начальное состояние механизма сохранения. Копия и журнал
  должны быть на Mac и в проверенном постоянном разделе U1, не в очищаемом
  overlay и не в `/userdata/.tmp` (его содержимое чистится при загрузке).
- Выполнить испытанный переход с остановкой, записью и запуском. Применять
  только свежий план. Не менять штатный RFID-драйвер, калибровки и параметры MCU.
- Проверить `ready`, состояние `tracker_uid`, четыре канала, штатную работу
  драйвера, затем реальные метки. Проверку UID отделить от автоматического
  списания: чтение UID само по себе не разрешает изменение остатков.
- Проверку после выключения питания согласовать отдельно в рамках физического
  испытания; наличие успешного процесса после установки её не заменяет.

### 4. Будущий откат

- Иметь независимый SSH-доступ и локальную копию инструкций, не зависящие от
  Tracker, его базы и рабочего интерфейса Moonraker.
- При остановленном Klipper сначала исключить активацию модуля: убрать только
  наш include-блок. Сохранить последующие чужие изменения основного конфига.
- Удалять только принадлежащие данной установке файлы после сверки хешей.
  Отдельно учесть созданный Python bytecode; неизвестные файлы не удалять.
- Восстановление глобального режима сохранения нельзя делать вслепую: если
  он изменялся, сверить начальное состояние и другие возникшие изменения.
  Не удалять весь overlay ради отката RFID и не менять чужие маркеры.
- Запустить принтер выбранным испытанным способом, проверить штатный ready и
  отсутствие нашего канала; журнал и копии оставить для разбора.

## Граница доказанного

В этом этапе сделана read-only диагностика реального U1 и анализ его файлов.
Код приложения/модуля не менялся; модульные тесты повторно не запускались.
Прежние 986 passed / 3 skipped и 17 процессных сценариев не покрывают найденную
загрузочную политику Buildroot. Установку на физический принтер они пока не
обосновывают. Ничего не опубликовано, установленный Tracker и база не использованы.
