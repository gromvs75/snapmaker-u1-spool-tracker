# UID: проверка в процессах Klipper и Moonraker — 10 ноября 2026

Модуль `dev/klipper/tracker_uid.py` успешно загружен настоящим Klippy. Moonraker
получил его статус через Unix-сокет и предоставил HTTP и WebSocket API.
Прошли 23 интеграционные проверки; предыдущие 218 стендовых тестов также проходят.
Исправлений самого UID-модуля для этого запуска не потребовалось.

Это полноценная проверка **процессов и API**, но не реального оборудования:
RFID-радио, GPIO/SPI и MCU заменены отдельными стендовыми фикстурами.
Принтер, установленный Tracker и пользовательские базы не использовались.

## Проверенная цепочка

`оригинальный поток FM175XXReader → оригинальная активация/каскады UID →
обёртка → настоящий reactor.register_async_callback → Klipper get_status/webhook →
Unix socket → Moonraker → HTTP/WebSocket клиент`.

- Неизвестная Mifare: `04112233`, канал 0.
- Пустая NTAG: `04112233445566`, канал 1, все семь байтов сохранены.
- Штатный callback для Mifare остался таким же, как без обёртки: ошибка чтения
  защищённых данных. Наличие UID не превращается в распознанный материал.
- Очистка канала 0 убирает его UID и не затрагивает канал 1.
- Настоящий `RESTART` создаёт новый `epoch`, старые UID не сохраняются.
- Неизвестный SHA драйвера выключает наблюдатель (`unavailable`), при этом
  Klipper остаётся `ready`.

Проверены адреса API:

```text
GET  /printer/objects/list
GET  /printer/objects/query?tracker_uid
GET  /printer/tracker_uid/status
WS   /websocket
     printer.objects.subscribe {"objects":{"tracker_uid":null}}
     notify_status_update
```

Подписка возвращает начальное состояние и затем действительно доставляет UID
асинхронным уведомлением. Пользовательский endpoint только читает состояние.
`bench_radio/scan` и `bench_radio/clear` существуют исключительно в тестовой
фикстуре и не входят в модуль для принтера.

## Найденное требование к клиенту Tracker 2.0.0

Доступность `/printer/info` и ответ `ready` не гарантируют, что Moonraker уже
зарегистрировал новый пользовательский endpoint: обнаружение API ещё может
продолжаться. Это воспроизвелось на стенде как кратковременный HTTP 404.

После подключения клиент должен проверять наличие `tracker_uid` и готовность
endpoint, повторяя запрос с ограниченным ожиданием. Не следует сразу объявлять
модуль отсутствующим или повторно устанавливать его. После смены `epoch` клиент
должен сбросить наблюдения старого процесса и заново оформить подписку.
После окончательного удаления модуля endpoint недоступен и объект исчезает.

## Установка и откат

1. Проверен запуск Klipper без UID-модуля и сохранён штатный результат сканирования.
2. Klipper остановлен, установщик добавил отдельный extra и include в конфиг.
3. После запуска модуль автоматически подключился до `ready`.
4. Попытка отката с маркером работающего Klipper была отклонена.
5. После остановки откат восстановил исходный `printer.cfg` побайтно, удалил
   модуль и `tracker_uid.cfg`. Установщик не менял файл RFID-драйвера.
6. Klipper повторно вышел в `ready`; UID-объекта больше нет, штатное сканирование
   вернуло тот же результат, что до установки. Повторный откат безопасен.

Отрицательная проверка неизвестного драйвера временно добавляла комментарий
**только в его одноразовую копию на стенде**, затем восстанавливала исходные байты.
Это отдельная тестовая мутация, не действие установщика.

## Окружение и ограничения

- macOS arm64, Python 3.11.16; рабочая папка `/private/tmp/tracker-uid-live`.
- Klipper: `56a9c605e121c6560f5c8b6c0e33bdda86de69a1`.
- Moonraker: `b559b9a81161f958a43c2f527b6ad96f73310d5d`.
- Snapmaker reader: 2.1.0.157, SHA256
  `ce7363f8b512e5474d18bd57cdf0660e6e2df57dc256e22f743b3b28c1b70be8`.
- HTTP только `127.0.0.1:18726`; собственные конфиги, БД и сокеты.
- MCU работает в штатном debug-output режиме Klipper с синтетическим словарём;
  движения, нагрев и соединение с аппаратным MCU отсутствуют.
- C helper собран Clang с двумя локальными заголовками совместимости macOS.
  Отслеживаемые исходники ядра Klipper и Moonraker не изменены.
- Moonraker использует штатные настройки `provider: none` и
  `file_system_observer: none`. Диагностические ошибки Linux-функций (`ip`,
  D-Bus, `/proc`, `SO_PEERCRED`) ожидаемы на Mac; они не скрывались.
- Проверка не подтверждает установку в Linux/overlay U1, совместимость всех
  версий его Klipper/Moonraker, физическое чтение любых меток или работу Windows.

Для плана 2.0.0: архитектура отдельного extra с обёрткой в памяти прошла
интеграционный этап. Далее — клиентский адаптер Tracker и несколько изолированных
экземпляров принтера; перед любым реальным развёртыванием отдельно проверить
целевые версии и механизм установки/отката U1. Разрешения трогать принтер нет.
