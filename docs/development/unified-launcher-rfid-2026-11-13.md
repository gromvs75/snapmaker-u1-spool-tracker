## Что подключено

`src/tracker_uid_launcher.py` — общий запуск GUI, Session, UID-клиентов и сборщиков.
Прежний стендовый run.py теперь только вызывает этот launcher; packaged app.py
использует тот же модуль. Старый релизный run_tracker.py не переключался.

Из сохранённых в GUI настроек создаются для каждого постоянного printer_id:
- UidClient для полных снимков tracker_uid;
- отдельный motion WebSocket и UID-only recorder;
- независимый поток чтения истории и проверки профиля текущего задания.

Все записи идут через единственный AccountingOwner SQLite. Кнопки подключения и
остановки GUI управляют всей связкой. При остановке сначала завершаются производители,
потом владелец базы. При сбое запуска HTTP-моста владелец также корректно закрывается.
Для стенда остаётся явный allowlist адресов; пустой список не разрешает подключений.

`tracker_uid_recorder.py` перенесён из проверенного lifecycle-стенда в src. Убраны
legacy-ветви commit_stream_estimate/commit_unchanged_slicer_estimate и самостоятельный
старый цикл запуска. На старте фиксируются доступные подтверждённые физические катушки;
движения головки без начальной привязки не дают списания. Журналы разных принтеров
разделены: ранее общий logger мог записывать события в файлы обоих сборщиков.

`tracker_uid_collectors.py` получает профиль через read-only API Moonraker:
активная история → текущий print_stats/mapping → метаданные и G-code → повторная
проверка метаданных, mapping и идентичности активного задания. Проверяются размер,
изменение файла, SHA256, параметры используемых логических инструментов. Не вводятся
плотность/диаметр по умолчанию. Нет единственного активного задания, доступного файла
или корректных параметров — нет доказанного профиля и автоматического списания.
Проверенный профиль привязан к job_id/start_time/filename, не одному имени файла.

HTTP приложения использует только GET; WebSocket только чтение/подписки. POST для
создания синтетических событий и metascan используется исключительно управляющим
скриптом стенда. Сборщики не вызывают паузу, печать, сканирование радио или команды U1.
При остановке HTTP-проверки прерываются между ограниченными по времени чтениями.

Автодозаправка не разрешена: изменившийся mapping/неединичный replenished блокируют
профиль и завершение расхода. Допуски motion и алгоритмы текущего ledger не изменялись;
константа смещения не вводилась. Исследование остаётся отдельным.

## Чтение меток — обязательная цепочка 2.0

На процессных стендах проверена цепочка штатного драйвера со смоделированным радио:
FM175xx → модуль tracker_uid → Moonraker → UidClient → SQLite → GUI → списание по UID.
Это не проверка физических антенн или реальных меток на U1.

- Зарегистрированные UID длиной 4 и 7 байт распознаны на разных принтерах.
- GUI показывает обе катушки как «Распознана по RFID» на правильных головках.
- После 100 мм движения расход 298 мг относится к соответствующей физической катушке.
- Перенос UID A:T0 → B:T2 сохраняет spool_id и остаток.
- Один UID на двух местах даёт conflict, обе позиции unusable.
- Новая 10-байтовая метка прочитана как needs_registration. Никакой катушки,
  остатка или материала из одного UID приложение не выдумывает.
- Обрыв снимает подтверждение UID; другой принтер продолжает работу.
- После переподключения UID распознаётся заново, но это не восстанавливает потерянное
  доказательство непрерывности уже прерванной печати.

UID — идентификатор катушки, а не её остаток или универсальный формат материала.
Первичная регистрация неизвестного UID пока доступна модели/API владельца;
отдельный пользовательский GUI этого действия ещё нужен. Неизвестная метка присутствует
в /api/state (occupied, needs_registration), но полноценная карточка регистрации
в этом этапе не добавлялась. Ручные назначения остаются для катушек без меток.

Для реального U1 требуется совместимый модуль tracker_uid на стороне Klipper;
штатный Moonraker сам по себе этот контракт не предоставляет. В этой работе модуль
на реальный принтер не устанавливался. Проверка физического чтения ещё впереди при
отдельном разрешении пользователя.

## Запуск только изолированного стенда

```sh
PYTHONPATH=src python -m tracker_uid_launcher \
  --data /private/tmp/my-uid-bench --port 18773 \
  --allow-url http://127.0.0.1:18771 --allow-url http://127.0.0.1:18772
```

Для нативного окна добавить `--window`; сначала нужны отдельно запущенные стенды.
Подключения сохраняются через GUI, запуск после открытия остаётся явным.
Воспроизводимый процессный тест: `python dev/labs/uid_launcher_bench/run.py`.
Он требует подготовленных зависимостей `/private/tmp/tracker-uid-live` и работает
только с маркированными no-hardware клонами. `--browser` оставляет окно для GUI-теста;
после browser.js создать `output/launcher-live/go` для продолжения.
