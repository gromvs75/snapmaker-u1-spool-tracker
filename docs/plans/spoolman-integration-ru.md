# План интеграции Tracker со Spoolman

Дата: 2026-11-05. Статус: этапы 1–5 реализованы в Preview; этап 6 — сборки и проверка.
Реальная пользовательская проверка и выпуск ещё не выполнены.
Результат: [контракт API и проверка сбоев](spoolman-api-contract-ru.md).
Preview поддерживает чтение и отправку расхода с остановкой на неоднозначном ответе.
Слепой автоматический повтор списания запрещён.
Номер релиза интеграции пока не назначен.

## Цель и границы

Дать пользователю возможность подключить существующий Spoolman как общий каталог
катушек и источник остатков, сохранив работу Tracker с оригинальной прошивкой U1
и привычный прогноз после нарезки в Snorca. Spoolman необязателен: автономный
режим Tracker продолжает работать без сервера.

Не менять прошивку или конфигурацию U1, Snorca, установленный Tracker и реальные
пользовательские данные во время разработки. Все проверки сначала проводить
на изолированном стенде с искусственными катушками и записями печати.
Не включать RFID-программирование, поддержку кастомной прошивки, автоматическую
калибровку расхода и синхронизацию профилей слайсера в эту интеграцию.

## Согласованные правила

- Snorca даёт прогноз расхода; нарезка и повторная нарезка ничего не списывают.
- Tracker наблюдает за U1 и применяет существующие правила допустимости учёта.
  Неопределённую печать нельзя отправлять в Spoolman как подтверждённый расход.
- Для подключённой катушки основной остаток хранится в Spoolman. Локально
  сохраняются история, связь с катушкой, очередь операций и кэш с временем чтения,
  но не второй независимо изменяемый баланс.
- За одну печать расход отправляет один участник. Режим «только чтение» нужен,
  если расход этого принтера уже передаёт другая интеграция. Автоматическое
  обнаружение всех внешних отправителей не обещаем.
- Материал и цвет, выбранные на экране U1, помогают проверить соответствие,
  но не идентифицируют конкретную катушку. Одинаковые материалы могут иметь
  разные остатки. Доступность полей через штатный API проверяется отдельно.
- Родные метки хорошо распознаются по проверке пользователя. Уже существующую
  обработку CARD_UID и привязку метки не выдаём за новую функцию интеграции.
- v1.4: проверка остатка по весам и отдельная подтверждённая корректировка —
  будущая задача, не условие запуска Spoolman. Текущий расчёт не меняем.

## Этап 1. Контракт API и изолированный стенд

- Выбрать и зафиксировать поддерживаемую версию Spoolman, сверить её API и MIT.
- Проверить получение катушек, остатка, материала, цвета, архивного состояния;
  способ передачи расхода, единицы и точность, ограничения отрицательных остатков.
- Отдельно выяснить поддержку идентификаторов операций, журнала списаний,
  атомарных изменений и поведения при повторных запросах. Не предполагать,
  что API гарантирует однократное выполнение.
- Развернуть тестовый Spoolman с отдельным хранилищем и фикстурами, без доступа
  к рабочей базе пользователя и без подключения к реальному U1.
- Описать адрес сервера, авторизацию, таймауты и ошибки; секреты не включать
  в обычные экспорты и логи.

Готово, когда: документирован проверенный контракт API и воспроизводятся
успешный запрос, недоступный сервер, отказ доступа и потеря ответа на запись.
До выбора безопасного протокола запись расхода не включать.

## Этап 2. Чтение каталога и привязка T0–T3

- Добавить необязательное подключение и режим только чтения.
- Хранить связь «экземпляр Spoolman + ID катушки»; ID другого сервера не считать
  той же катушкой. Переключение сервера требует явного переназначения.
- Выбирать существующие катушки для T0–T3 без массового импорта, создания
  дубликатов или перезаписи локального инвентаря.
- Обрабатывать удалённые/архивные катушки, потерю подключения и устаревший кэш.
- Определить правила назначения одной катушки нескольким головкам; не допускать
  независимой проверки полного остатка для каждого такого назначения.

Готово, когда: на стенде видны реальные остатки тестового сервера, назначения
  сохраняются после перезапуска, а чтение не изменяет ни одной катушки Spoolman.

## Этап 3. Прогноз Snorca с остатками Spoolman

- Подключить внешний источник остатков к существующему прогнозу и меню,
  не менять механизм наблюдения за нарезкой.
- Перед проверкой обновлять остатки. Показывать источник и свежесть данных;
  недоступность сервера не представлять как свежий положительный результат.
- Суммировать потребность, если несколько назначений относятся к одной катушке.
- Сохранить резерв, оценочный характер расхода, указание плиты, используемых
  головок и допущения о соответствии материалов T0–T3.
- Проверить одноцветную/многоцветную печать, нехватку, повторную нарезку,
  изменение остатка извне и отсутствие сервера.

Готово, когда: прогноз использует правильные остатки и ни нарезка, ни просмотр
меню, ни перезапуск не отправляют расход. Это первый пользовательский тестовый
этап; автоматическое списание пока выключено.

## Этап 4. Передача расхода без двойных списаний

- Встроить внешний получатель расхода в существующий учёт, сохранив автономный
  режим. Зафиксировать катушки для конкретной печати, а не использовать текущие
  назначения после её завершения.
- Записывать устойчивую операцию локально до отправки: принтер, уникальный запуск
  печати, катушка, сумма, основание расчёта, статус. Для одной катушки агрегировать
  расход; одинаковый файл, напечатанный дважды, означает два разных запуска.
- Использовать устойчивую очередь. Отдельно показывать учтённый расход,
  ожидающую отправку, подтверждение сервера и неопределённый результат.
- При потере ответа после возможного списания не повторять запрос вслепую.
  Если API не позволяет доказать применение операции, нужна сверка/ручное
  разрешение неопределённости. Изменение остатка само по себе не доказывает
  выполнение нашей операции, особенно при других принтерах и ручных правках.
- Не перезаписывать абсолютный остаток устаревшим локальным значением.
- Обработать частичное выполнение для нескольких катушек: подтверждённые
  операции повторно не отправлять; неподтверждённые разбирать отдельно.
- Сохранить существующие ограничения учёта отменённых и неоднозначных печатей.
- Учесть повторное получение истории, перезапуск, повторное подключение,
  смену катушки во время печати и восстановление старой резервной копии.
- Режим чтения никогда не отправляет расход; переключение режима не запускает
  массовое списание старой истории. Несколько экземпляров Tracker не должны
  независимо отправлять расход одного U1.

Готово, когда: тесты со сбоями подтверждают отсутствие повторных списаний,
потерянные подтверждения остаются видимыми и не маскируются как успех.

## Этап 5. Настройка, отключение и резервные копии

- Сделать выбор режима понятным: автономный, Spoolman только чтение,
  Spoolman с передачей расхода от Tracker.
- Объяснить пользователю, кто списывает расход; настроить доступность сервера,
  переназначение и разрешение ошибок очереди.
- Отключение интеграции не удаляет данные сервера. Переход к автономному балансу
  выполнять как явный перенос с показом свежести данных и неотправленных операций.
- Восстановление резервной копии не должно повторно отправлять прежние списания.
- UI-проектирование проводить по правилам AGENTS.md с Lazyweb; на этапе этого
  текстового плана продуктовый интерфейс не меняется.

Готово, когда: режимы и восстановление проверены на стенде, пользователь может
понять текущий источник остатка и состояние каждой неподтверждённой операции.

## Этап 6. Тестовые сборки и выпуск

- Прогнать значимые регрессионные проверки автономного учёта, прогнозов,
  резервных копий и нового протокола интеграции.
- Подготовить отдельную Mac-сборку с отдельными тестовыми данными, не заменяя
  установленный Tracker. Реальную проверку пользователь проводит отдельно.
- Подготовить Windows-сборку; сохранить явную пометку: Windows GUI и реальная
  нарезка Snorca на Windows не проверены, пока фактический тест не выполнен.
- Обновить руководства: оригинальная прошивка, необязательность Spoolman,
  установка отдельного сервера, режим единственного отправителя, ограничения.
- Назвать Spoolman и дать ссылку на проект; при включении чужого кода сохранить
  необходимые уведомления и проверить лицензии включаемых зависимостей.
- Публикация релиза — отдельное поручение пользователя.

Готово, когда: пользователь проверил тестовую сборку, ограничения указаны,
результаты проверок сохранены и нет нерешённых рисков повторного списания.

## Точки принятия решений

1. После этапа 1: выбрать безопасный протокол записи или ограничить первую
   версию чтением; не обещать «ровно один раз» без доказательств.
2. После этапа 3: проверить полезность реального прогноза с внешним каталогом.
3. После этапа 4: разрешать передачу расхода только при проверенной обработке сбоев.
4. После этапа 6: определить номер и готовность релиза.
