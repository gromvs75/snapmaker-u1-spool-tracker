# RFID: холодный старт и откат на стенде — 17.11.2026

## Результат

**Обычная установка трёх файлов недостаточна для выявленной загрузочной схемы
U1. Ошибка после очистки системного слоя воспроизведена на двух процессных
стендах.** Условный вариант с явным сохранением всего overlay переживает
моделируемые холодные старты и границы прерываний установки/отката.

Это ещё не готовый пакет для физического принтера: включение `/oem/.debug`
имеет системный эффект, а весь фактический overlay и поведение обновления
прошивки не воспроизведены. Маркер на реальном U1 не создавался.

## Контрольная точка и область изменений

Документы предыдущей диагностики сохранены коммитом `c6c1082`.
Контрольная ветка: `checkpoint/rc17-before-rfid-boot-lifecycle`.
Рабочая ветка этапа: `integrate/2.0-rfid-boot-lifecycle`.

До изменений прежняя регрессия: **986 passed / 3 skipped**, 158.28 с,
`output/rfid-boot-baseline-localhost.log`. Первый запуск в sandbox не разрешил
bind localhost (61 failed, 44 errors, 881 passed, 3 skipped); его журнал сохранён
как `output/rfid-boot-baseline.log`. Повтор с доступом к локальным портам прошёл.

Добавлены только лабораторная модель, процессный сценарий, тесты и документация:

- `dev/labs/uid_boot_bench/model.py` — модель загрузочной политики и явно
  подтверждаемый эксперимент с сохранением overlay;
- `dev/labs/uid_boot_bench/run.py` — два настоящих процесса Klipper/Moonraker,
  точный закреплённый драйвер 2.1.0.157, имитация RF/SPI/MCU;
- `tests/test_rfid_boot_model.py` — проверки загрузки и прерываний;
- `dev/labs/uid_boot_bench/README.md` — запуск и ограничения модели.

Основной установщик, UID-модуль, GUI, языки, учёт и очередь Spoolman не менялись.
Новый EXE/app не собирался; приложение остаётся rc17. Реальный U1 в этом этапе
не использовался даже для диагностики; установленный Tracker, рабочие базы и
Spoolman не открывались. Ничего не публиковалось.

## Варианты

| Вариант | Результат | Решение |
| --- | --- | --- |
| Extra + cfg + include, сохранение overlay выключено | После загрузки модуль исчезает, конфиг остаётся, реальный Klipper выдаёт invalid config section | Не использовать для U1 |
| Явное сохранение всего overlay до активации модуля | Холодные старты, новые эпохи UID, установка и откат на проверенных границах прошли | Кандидат только с отдельным согласованием системного режима |
| Выборочный постоянный boot-hook | Поддерживаемая точка загрузки ранее не найдена; вариант не реализован | Не выдавать за существующее решение |

Ошибка первого варианта: `Section 'tracker_uid' is not a valid config section`,
`Printer is halted`. Полные сообщения — `output/rfid-boot-process/a-naive-boot-error.txt`
и `b-naive-boot-error.txt`. Откат вернул штатный `ready` на обоих стендах.

## Последовательность кандидата

Постоянный план → явное согласие на сохранение overlay → маркер сохранения →
модуль → cfg → include. Копии и журнал прежнего установщика лабораторный адаптер
размещает в постоянной области. Прерванную установку сначала откатывают, затем
создают новый план; повтор поверх незавершённой записи запрещён.

Откат: include → cfg → модуль и только его cache → созданный испытанием маркер.
Чужая исходная настройка сохранения не удаляется. При чужих изменениях исходников
моделируемого системного дерева маркер сохраняется для ручного разбора. Повреждённая
запись или изменённый чужим кодом модуль блокируют разрушительный откат.
После прерывания новый контроллер восстанавливает операцию по постоянному журналу.

## Обновление прошивки

Наблюдавшийся `systemUpgrade.sh` удаляет сначала `.printer_data`, затем `.debug`.
Модель проверяет остановку после первого удаления и после обоих: восстановление
исходного конфига отключает extra. Это не испытание настоящего OTA.

Потеря **только** `.debug` при сохранении пользовательского конфига продолжает
вызывать ошибку. Это отдельный сценарий потери маркера, не утверждение о порядке
действий наблюдавшегося updater. Контролируемый путь — полностью убрать интеграцию
UID до обновления — прошёл. Стенд не может принудить будущий OTA на реальном U1
пройти через этот сценарий. Универсальная устойчивость к OTA не подтверждена.

Неизвестный хеш драйвера при доступном модуле оставляет Klipper в `ready`, а
observer переходит в `unavailable`. Это отдельно подтверждено процессными проверками.

## Ограничения и следующий этап

Модель использует обычные каталоги, а не kernel OverlayFS. Она проверяет поддерево
Klipper, не весь системный overlay. Прерывания внедрены между файловыми операциями;
это не настоящие отключения питания и не доказательство аппаратной надёжности fsync.
Init-скрипты U1, MCU, watchdog/lmd не исполнялись. Данные о UID не используются
для списаний; правила автодозаправки не менялись.

Выбранный для дальнейшей подготовки кандидат — **явно согласованное сохранение
overlay**. До физической установки нужны полный учёт его системных последствий,
независимый аварийный откат и проверка жизненного цикла обновления прошивки.
Пока эти условия не закрыты, установка на U1 не предлагается. Не создавать
`.debug` автоматически и не превращать прежний `0.2.0-bench` в реальный установщик
обходом его ограничений.
